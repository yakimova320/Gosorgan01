# Ja!sno

Ja!sno помогает русскоязычным людям в Германии понять письмо от ведомства и ответить на него. Сайт открывается в браузере телефона, устанавливать ничего не нужно.

- Задание: `workflow/261116/11_TZ_ClaudeCode_v4_RU.md`
- Задачи: GitHub Issues, описание в `workflow/261116/12_Issues_GitHub_v4_RU.md`
- Решения: `docs/decisions.md`, команда: `docs/team.md`, готовность экранов и API: `docs/readiness.md`

## Из чего состоит

| Папка | Что это |
|---|---|
| `api/` | сервер (NestJS): хранит данные, говорит с языковой моделью, отвечает на запросы |
| `web/` | сайт (React + Vite) |
| `content/` | FAQ и карточки «Важно знать», их пишут люди |
| `fixtures/letters/` | 15 синтетических писем с ожидаемыми результатами |
| `docs/` | решения, команда, дизайн, готовность |

## Быстрый запуск

Нужно один раз: Node.js 24 и pnpm.

### Mac

1. Установить Node.js 24 LTS с сайта https://nodejs.org (файл `.pkg`, кнопка «LTS»).
2. Открыть «Терминал» и выполнить:

   ```bash
   corepack enable
   corepack prepare pnpm@latest --activate
   node -v
   pnpm -v
   ```

   `node -v` должен показать `v24...`.

### Windows

1. Установить Node.js 24 LTS с сайта https://nodejs.org (файл `.msi`, кнопка «LTS»). Галочки по умолчанию не менять.
2. Открыть «PowerShell» от имени администратора и выполнить:

   ```powershell
   corepack enable
   corepack prepare pnpm@latest --activate
   node -v
   pnpm -v
   ```

### Docker Desktop (для базы)

База PostgreSQL работает в Docker. Установить Docker Desktop: https://www.docker.com/products/docker-desktop/ и запустить его.

### Запуск проекта (Mac и Windows)

В терминале перейти в папку проекта (`cd` и путь к папке `Gosorgan01`) и выполнить:

```bash
pnpm install
```

Скопировать файл настроек сервера:

- Mac: `cp api/.env.example api/.env`
- Windows: `copy api\.env.example api\.env`

Без изменений файл работает в режиме `LLM_MODE=demo` (без настоящей модели). Для настоящей модели вписать в `api/.env` значения `LLM_MODE=openai`, `LLM_API_KEY` и `LLM_MODEL`. Ключ никому не отправлять и в git не добавлять.

Запустить базу PostgreSQL (Docker Desktop должен быть запущен):

```bash
pnpm db:up
```

Создать таблицы или обновить их после новых миграций:

```bash
pnpm db:migrate
```

Посмотреть таблицы в браузере: `pnpm db:studio`. Что в каких таблицах: [docs/database.md](docs/database.md).

Запустить сервер:

```bash
pnpm dev:api
```

Проверить в браузере:

- http://127.0.0.1:3000/health показывает `{"ok":true,...}`
- http://127.0.0.1:3000/docs открывает Swagger

Остановить сервер: `Ctrl + C` в терминале.

### Сайт

Во втором окне терминала:

- Mac: `cp web/.env.example web/.env`
- Windows: `copy web\.env.example web\.env`

```bash
pnpm dev:web
```

Открыть http://localhost:5173 (именно `localhost`: с адреса `127.0.0.1:5173` API запросы не примет — «Нет связи с сервером»).

**С телефона в той же сети Wi-Fi** (только дома, не в общественной сети). Адрес Mac: `ipconfig getifaddr en0`, ниже для примера `192.168.1.50`.

1. `api/.env`: `HOST=0.0.0.0`, `CORS_ORIGIN=http://localhost:5173,http://192.168.1.50:5173`, `APP_PUBLIC_URL=http://192.168.1.50:5173`.
2. `web/.env`: `VITE_API_URL=http://192.168.1.50:3000`, `VITE_DATA_MODE=api` (`demo` здесь не бывает: любое значение кроме `api` включает примерные данные).
3. Перезапустить `pnpm dev:api` и `pnpm --filter jasno-web dev --host 0.0.0.0` (без `--` перед `--host`). В выводе должна быть строка `Network: http://192.168.1.50:5173/`.
4. На телефоне `http://192.168.1.50:5173`: в углу «сервер», жёлтой плашки «Примерные данные» нет. Проверка API: `http://192.168.1.50:3000/health`.
5. После теста вернуть прежние значения (`HOST=127.0.0.1` и адреса `localhost`).

В `web/.env` переменная `VITE_DATA_MODE=mock` включает примерные данные: сайт работает без сервера, в углу видна подпись «примерные данные». `VITE_DATA_MODE=api` берёт данные с сервера; экраны, для которых на сервере ещё нет функции, честно пишут «ещё не подключена».

Иллюстрации кладутся в `web/public/illustrations/` (список в `docs/design/README.md`).

## Проверки перед Pull Request

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm test:e2e
pnpm build
```

Все команды должны закончиться без ошибок. Те же проверки запускает GitHub Actions в каждом PR (`.github/workflows/ci.yml`).

`pnpm test:e2e` запускает тесты API и браузерные тесты Playwright (`web/e2e`). Для них нужна запущенная база (`pnpm db:up`) и один раз браузер: `pnpm --filter jasno-web exec playwright install chromium`. Браузерные тесты сами запускают API (порт 3100, своя схема базы, `LLM_MODE=demo`, без файлов `.env`) и сайт (порт 5174).

Офлайн-показ без сервера: `pnpm --filter jasno-web build:offline` создаёт один файл `web/dist-offline/index.html` с примерными данными. Он открывается двойным щелчком.

Из терминала (в папке проекта, сервер запущен):


## Восстановление пароля: где письмо

По умолчанию `MAIL_MODE=file`: письма никуда не отправляются, а сохраняются файлами. Так восстановление можно проверить без почтового сервиса.

1. На сайте: «Вход» → «Забыли пароль?», ввести адрес своего тестового аккаунта.
2. Письмо появится через пару секунд в папке `api/storage/mail-outbox/<id кабинета>/` (если в `api/.env` задан другой `STORAGE_DIR`, то в нём). Самое новое письмо:

   ```bash
   ls -t api/storage/mail-outbox/*/*.eml | head -1
   ```

3. Открыть файл `.eml` двойным щелчком (откроется в почтовой программе: Почта на Mac, Outlook или Thunderbird на Windows) и нажать ссылку. Если открыть файл как текст, ссылка тоже видна, но в ней вместо `token=` стоит `token=3D`, а длинная строка может быть перенесена знаком `=`: так кодируется письмо.
4. Ссылка ведёт на `APP_PUBLIC_URL/reset?token=…` (по умолчанию `http://localhost:5173`). Ссылка работает один раз и `RESET_TOKEN_TTL_MIN` минут (по умолчанию 60).

В файле действующая ссылка: файлы доступны только владельцу (права 0600), не раздаются сайтом, удаляются после сброса или смены пароля и при удалении аккаунта. Не пересылайте их. В `production` режим `file` запрещён.

Ограничения: не больше 3 писем в час на адрес (сверх этого ответ тот же, письма нет) и 10 запросов в час с одного IP. Если сервер стоит за прокси (nginx, Caddy), укажите его в `TRUST_PROXY` (например `loopback`), иначе все клиенты будут считаться одним IP.

### Настоящая отправка (smtp)

В `api/.env`:

```
MAIL_MODE=smtp
MAIL_FROM=Ja!sno <no-reply@ваш-домен>
SMTP_HOST=smtp.ваш-сервис
SMTP_PORT=587
SMTP_USER=…
SMTP_PASS=…
SMTP_SECURE=        # true только для порта 465
```

Ключи только в `api/.env`, не в git. Письмо отправляется в фоне: при сбое сервер повторит ещё 2 раза (через 1 и 5 минут). В лог и в базу пишется только код ошибки (например `EAUTH/535`), без адреса и текста ответа сервиса. Почтовый сервис команда ещё не выбрала (ТЗ v4, решение 16.11): режим smtp пока не проверен с настоящим сервисом.

## Оценка качества на 15 письмах (B14)

```bash
pnpm --dir api eval
```

Прогоняет 15 синтетических писем из `fixtures/letters` через настоящий путь API: загрузка → факты → подтверждение → дело → объяснение → черновик `CLARIFICATION`. Модель берётся из `api/.env` (`LLM_MODE`). Результат: `reports/eval-latest.md` (таблицы для слайда) и `reports/eval-latest.json`.

- Прогон идёт во временной схеме PostgreSQL `eval_…` и временном хранилище; они удаляются в конце и при ошибке. Ваши данные не затрагиваются.
- Предел обращений к модели (с повторами): `--max-calls 50` по умолчанию. Достигнут: прогон останавливается, отчёт помечается «частичный», итог по правилам «не оценено».
- Если провайдер модели отвечает «перегружен» (`LLM_QUOTA`), письмо помечается «не выполнено» и не входит в метрики; итог — «не оценено». Это не оценка качества.
- `--only 01_jobcenter_request,04_buergeramt` — только эти письма; `--render-only` — пересобрать `.md` из сохранённого `.json` без обращений к модели.
- Итог «принято / не принято» по Q1–Q5 и порогам: 0 выдуманных дат и сумм, ведомство и номер дела верны не меньше чем в 12 письмах, понятные отказы, письмо 14 без выполненных команд. Ожидаемые отказы (нечитаемое фото, сканы PDF) считаются отдельно. Эталоны не меняются ради прохождения.
- `LLM_MODE=demo pnpm --dir api eval` проверяет механизм оценки, а не качество модели. Автоматические проверки не заменяют смысловую приёмку человеком. Стоимость письма: «цена не задана», пока не указан проверенный прайс.

## Лимиты (B18)

| Что | Лимит | Ответ |
|---|---|---|
| Вход | 20 запросов за 15 минут с одного IP (и 4 неудачные попытки на e-mail за 15 минут) | 429 `RATE_LIMITED` |
| Регистрация | 5 в час с одного IP | 429 `RATE_LIMITED` |
| «Забыли пароль?» | 10 в час с одного IP, 3 письма в час на адрес | 429 / тот же 202 |
| Загрузка письма | 30 в час с одного IP | 429 `RATE_LIMITED` |
| Операции с моделью (загрузка письма, объяснение) | `LLM_DAILY_OPS_PER_CABINET` на кабинет за скользящие 24 часа (по умолчанию 30) | 429 `RATE_LIMITED` с временем ожидания и `Retry-After` |
| Общий расход модели | `LLM_DAILY_TOKEN_BUDGET` токенов за 24 часа на все кабинеты (по умолчанию выключен) | 503 `LLM_QUOTA` |

- Операция резервируется перед первым обращением к модели, после проверки файла и кэша объяснения: неверный файл и объяснение из кэша лимит не тратят. Фото (распознавание + факты) — одна операция, не больше 3 обращений к модели вместе с повторами.
- Общий порог — мягкий: проверяется перед каждым обращением, включая повторы, но расход обращения становится известен только после ответа, поэтому несколько одновременных операций могут превысить порог. Это не гарантия расходов: лимит у провайдера модели настраивается отдельно. Учёт расхода (`LlmUsageHour`) не содержит данных пользователей и не уменьшается при удалении писем и аккаунтов. Ответ без данных о токенах считается по длине текста, а не нулём.
- Счётчики по IP хранятся в памяти процесса: после перезапуска API начинаются заново и не делятся между несколькими экземплярами API. За прокси (nginx, Caddy) укажите его в `TRUST_PROXY`.

## Разовая очистка аккаунтов

Удаляет аккаунты вместе с их данными: сессиями, токенами восстановления, делами, письмами, фактами, черновиками, журналом `LlmCall`, файлами писем и письмами восстановления пароля. Это не часть запуска приложения: каждый запускает скрипт сам, для своей базы.

Сначала посмотреть, что будет удалено (ничего не удаляется):

```bash
pnpm --filter jasno-api db:wipe-accounts --all
```

Скрипт покажет цель: хост, порт, базу, схему (без пароля) и абсолютный путь хранилища. Проверьте, что это ваша база. Удаление — тем же запуском с `--confirm` и строкой цели, которую показал скрипт:

```bash
pnpm --filter jasno-api db:wipe-accounts --all --confirm localhost:5432/jasno/public
```

Вместо `--all` можно указать отдельные адреса: `--email anna@example.org`. Повторный запуск должен показать 0. Если удаление файлов прервалось, запустите ещё раз: кабинет удаляется из базы только после его файлов. При `NODE_ENV=production` скрипт отказывается работать.
