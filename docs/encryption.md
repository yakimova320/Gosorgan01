# Шифрование писем (E01, #163)

Техбриф: KORR/TechBrief_Daten-Schiffrierung. Цель: Supabase и сервер хранят только шифротекст и не имеют ключей, чтобы прочитать архив.

Решение владельца продукта 26.11: полное шифрование в браузере (вариант A), поиск по архиву по вектору обезличенного резюме. Исключения из брифа (ниже) одобрены 26.11. Проверку криптографом решено не проводить.

## Ключи

| Что | Где создаётся | Где хранится |
|---|---|---|
| Секрет восстановления: 32 случайных байта и 2 байта контрольной суммы, base32 группами по 4 знака | браузер, экран «Ключ вашего архива» | только у человека (показан один раз, можно скопировать или скачать файлом) |
| Мастер-ключ AES-256-GCM | браузер | на сервере только запись `jxm1` (`KeyVault`): ключ зашифрован ключом из секрета (HKDF-SHA-256 с солью) |
| Ключ документа (письмо, дело) AES-256-GCM | браузер, на каждый документ свой | на сервере только запись `jxk1` (`DocumentKey`), зашифрован мастер-ключом |
| Ключ устройства | браузер | IndexedDB, неизвлекаемый `CryptoKey`: им зашифрован мастер-ключ, чтобы на этом устройстве не вводить секрет каждый раз |

- Каждое шифрование получает новый IV длиной 12 байт.
- AAD = версия формата + кабинет + документ (`keyId`).
- Своей криптографии нет: только Web Crypto (`packages/shared/src/crypto.ts`). Этот же код работает и в браузере, и в Node.
- Открытые ключи живут только в памяти модуля `web/src/crypto/keyring.ts`: не в Redux, не в localStorage, не в журнале.
- Выход из аккаунта и истёкшая сессия стирают их из памяти (`lockKeyring`).
- Удаление аккаунта удаляет и запись устройства.
- Сброс пароля `KeyVault` не трогает: архив открывается только секретом.
- Если потерять секрет и все разблокированные устройства, письма будут потеряны навсегда. Экран создания ключа объясняет это до первой загрузки.

## Что зашифровано

| Таблица или место | Шифротекст | Открыто |
|---|---|---|
| `Letter` | `rawText`, `title`, `explanation`, `translation` | вид файла, число страниц, размеры, даты |
| хранилище (локальная папка или private bucket Supabase) | оригиналы, формат `JXB1` | путь: случайный ключ, без имени файла |
| `Claim` | `text`, `quote`, `value` (кроме дат) | вид факта, статус; значение у `LETTER_DATE` и `DEADLINE` |
| `Case` | `title`, `authority`, `caseNumber` | статус, вид дела |
| `Draft` | `germanText`, `russianText`, значения фактов в `claimSnapshot`, проверки в `verification` | вид, статус, номер письма и шаблона, итог проверки |
| `LetterSummary` | обезличенное резюме (`de`, `local`) | вектор резюме |
| `LlmCall` | — | вместо текста только размер: «[письмо зашифровано: N знаков]» |

Формат поля: `jx1.<t|j>.<keyId>.<iv>.<шифротекст>`, где `t` — текст, `j` — JSON.

## Как сервер работает с письмом

- Просмотр (GET) сервер отдаёт шифротекстом, расшифровывает браузер (`web/src/store/baseQuery.ts`).
- Действия, которым нужен текст, сначала получают от сервера `428 KEYS_REQUIRED { keyIds }`: загрузка, объяснение, перевод, подтверждение и исправление факта, новое дело, черновик, PDF, вопрос к архиву. Браузер повторяет запрос с ключами именно этих документов (`x-jasno-keys`).
- Сервер держит ключи только на время запроса (AsyncLocalStorage) и удаляет заголовки из запроса сразу после разбора.
- Новый документ получает ключ из заголовка `x-jasno-new-key`. Его браузер прикладывает к каждому запросу-действию; сохраняется он, только если документ создан.
- ИИ получает текст только по действию человека и при согласии K11.
- Подмена данных:
  - изменённый байт шифротекста даёт `422 INTEGRITY_FAILED`;
  - шифротекст другого письма в полях письма тоже даёт `422 INTEGRITY_FAILED`: проверяется `keyId` объекта.

## Поиск по архиву

- При загрузке тот же вызов `extract.v5` возвращает резюме на немецком и на языке кабинета.
- Код проверяет, что резюме обезличено (`api/src/archive/summary-check.ts`). Отклоняется резюме, где маскирование находит личные данные, есть числа из 4 и больше цифр или имя, фамилия и улица из профиля.
- Вектор резюме считается в памяти и хранится открыто. Само резюме хранится зашифрованным.
- Вопрос: сервер ищет по векторам только этого кабинета и просит ключи найденных писем. Модели уходят резюме и по 2 куска каждого найденного письма; цитаты проверяются по тексту письма.

## Одобренные исключения и границы

1. Открыт вектор резюме. По нему можно примерно восстановить тему письма (например, «Jobcenter, документы»), но не имя и не номер.
2. Открыты дата и вид срока: они нужны для напоминаний по e-mail и календаря. Напоминание и лента .ics не содержат ведомства и названия дела зашифрованных писем.
3. Обработка идёт на сервере. По действию человека открытый текст на время запроса есть на сервере и у модели ИИ, но не сохраняется. OCR и ИИ в браузере не выполняются.
4. Не зашифрованы: профиль (имя, адрес, номера) и чат-помощник без писем. Это не архив писем.
5. Факты одного письма можно переставить между собой, но не подставить из другого письма: AAD привязан к документу, а не к строке.
6. Шифрование не защищает от заражённого устройства, XSS и подменённого кода сайта. Защита — строгая CSP (`api/src/web/web-static.ts`) и никаких сторонних скриптов: внешние только шрифты Google.

## Письма до шифрования

- Письма и дела с `keyId = null` браузер шифрует сам после открытия архива: `POST /crypto/legacy`, по одному за запрос.
- У таких писем нет резюме, поэтому в поиск по архиву они не попадают (`pendingLetters`).
- Миграция `20261126140000_letter_encryption` удаляет `LetterChunk`: там лежали открытые куски писем.

## Настройки

- `ENCRYPTION_REQUIRED`: по умолчанию `true`, кроме `NODE_ENV=test`. В production `false` нельзя.
  - Без ключа архива загрузка письма получает `409 ENCRYPTION_SETUP_REQUIRED`.
  - Postman-коллекция ключ архива создать не может (нет AES-GCM), поэтому её запускают с `ENCRYPTION_REQUIRED=false`.
- `DEMO_RECOVERY_SECRET`: секрет восстановления демо-кабинета (`pnpm db:seed`). Его вводят в браузере при первом входе на устройстве. Если переменной нет, seed подсказывает новый секрет.
