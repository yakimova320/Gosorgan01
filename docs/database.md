# База данных Ja!sno простыми словами

Для Дмитрия (сверка D02) и всех, кто смотрит базу в Prisma Studio.

Схема лежит в `api/prisma/schema.prisma`. Это единственный файл, который правят руками. Основа: ТЗ v2 раздел 7, изменения: ТЗ v4 раздел 8.

## База

Только PostgreSQL: на своём компьютере, в тестах, в CI и на сервере (TechBriefing v5, раздел 3). Для разработки база работает в Docker, файл `docker-compose.yml` в корне проекта.

Адрес базы в `api/.env`: `DATABASE_URL=postgresql://jasno:jasno@localhost:5432/jasno`. Пароль `jasno` только для локальной базы в Docker, на сервере другой.

## Команды

| Команда | Что делает |
|---|---|
| `pnpm db:up` | запускает PostgreSQL в Docker и ждёт, пока база будет готова. Нужен запущенный Docker Desktop |
| `pnpm db:migrate` | применяет к базе новые миграции. После правки схемы создаёт новую миграцию |
| `pnpm db:studio` | открывает Prisma Studio в браузере: таблицы и строки |
| `pnpm db:seed` | начальные данные. Пока пусто, демо-кабинет добавит задача B19 |
| `pnpm db:down` | останавливает базу. Данные остаются в томе Docker `jasno-db` |

Миграции лежат в `api/prisma/migrations/`. Каждая миграция — папка с файлом `migration.sql`. Старые миграции не меняют, только добавляют новые. Миграции времён SQLite лежат в архиве `api/prisma/migrations-sqlite-archive/` и не применяются.

Данные переживают перезапуск: `docker compose restart db`, потом вход тем же паролем.

Начать с пустой базы (все локальные данные пропадут): `docker compose down -v`, затем `pnpm db:up` и `pnpm db:migrate`.

Тесты создают для каждого тестового файла свою схему `test_<id>` в той же базе и удаляют её после прогона. Другая база для тестов: переменная `TEST_DATABASE_URL`.

Старый файл `api/dev.db` от SQLite больше не используется. Его можно удалить вручную, проект его не трогает.

## Таблицы

Главная таблица — **Cabinet** (кабинет, то есть аккаунт). Почти всё остальное принадлежит кабинету. Если удалить кабинет, база сама удалит всё, что от него зависит (каскад). Исключение: **LlmCall**, её строки удаляет код.

```text
Cabinet
├── Session              входы (сессии)
├── PasswordResetToken   ссылки восстановления пароля
├── Letter               письма во «Входящих» (без дела)
└── Case                 дела
    ├── Letter           письма дела
    │   ├── Claim        факты из письма
    │   │   └── Deadline срок (если факт — срок)
    │   └── Deadline
    ├── Claim            факты, которые сказал пользователь
    ├── Event            история дела
    ├── Message          вопросы и ответы по делу
    └── Draft            черновики ответа
LlmCall                  журнал обращений к модели (без связей)
AccountErasure           задание удаления аккаунта (без связей)
```

### Cabinet — кабинет

Один пользователь, один кабинет.

| Поле | Что это |
|---|---|
| `email` | e-mail для входа, всегда маленькими буквами, второй такой же нельзя |
| `passwordHash` | хэш пароля (bcrypt). Самого пароля в базе нет |
| `passwordChangedAt` | когда пароль меняли. Сессии, у которых `passwordAt` раньше этого момента, больше не работают |
| `language` | язык интерфейса, сейчас `ru` |
| `profile` | имя, адрес, номера (Kundennummer и др.) для подписи в письмах |
| `consentAt` | когда пользователь поставил галочку согласия |
| `lastSeenAt` | последний визит. Нужен для автоудаления старых кабинетов |
| `deletingAt` | идёт удаление аккаунта (A01): записи запрещены. Это временная блокировка, не «мягкое удаление»: после удаления строки нет, при откате отметка снимается |

### Session — вход

Пока сессия жива, пользователь залогинен. В базе хранится только хэш токена (`tokenHash`), сам токен знает только браузер. `expiresAt`: когда сессия истекает.

`passwordAt` (A02): момент пароля, которым подтверждена сессия. При входе равен моменту входа. При смене пароля текущая сессия получает тот же момент, что и `Cabinet.passwordChangedAt`, поэтому остаётся рабочей; `createdAt` и `expiresAt` не меняются. Остальные сессии кабинета и все его ссылки восстановления пароля удаляются в той же транзакции.

### PasswordResetToken — ссылка «Забыли пароль»

Одна строка — одна отправленная ссылка. Хранится хэш токена, срок (`expiresAt`) и `usedAt`, если ссылкой уже воспользовались. Использованная или просроченная ссылка не работает.

### Case — дело

Папка для писем одной темы, например «Jobcenter, Weiterbewilligung».

| Поле | Что это |
|---|---|
| `title` | название дела |
| `authority`, `caseNumber` | ведомство и номер дела (Aktenzeichen) |
| `status` | `OPEN` (открыто) или `CLOSED` (завершено) |
| `origin` | `INCOMING`: началось с письма ведомства, `OUTGOING`: с нашего письма |

Надпись вроде «Нужен ответ» или «Просрочено» в базе не хранится. Её каждый раз считает код по срокам, фактам и черновикам (ТЗ v4 раздел 8).

### Letter — письмо

| Поле | Что это |
|---|---|
| `caseId` | пусто: письмо во «Входящих», ещё не разложено по делу |
| `sourceType` | `PDF_TEXT` (PDF с текстом) или `IMAGE` (фото, скан) |
| `rawText` | распознанный текст письма целиком |
| `pages` | страницы: номер, прочитана ли, сколько знаков |
| `files` | файлы-оригиналы: номер страницы, случайное имя файла в хранилище, тип, размер. Имени исходного файла нет |
| `explanation` | готовое объяснение письма. Стирается, когда меняются факты письма |

### Claim — факт

Одно утверждение о письме: «ведомство: Jobcenter», «срок: 01.12.2026», «сумма: 120 €».

| Поле | Что это |
|---|---|
| `kind` | вид факта: ведомство, номер дела, дата письма, требование, срок, сумма, другое |
| `value` | значение в строгом виде (дата `2026-12-01`) |
| `text` | то же по-русски для человека |
| `quote`, `page` | точная цитата из письма и страница. Цитата обязана быть в тексте письма |
| `basis` | `DOCUMENT`: из письма, `USER`: сказал пользователь |
| `status` | `UNCONFIRMED` (не проверен), `CONFIRMED` (подтверждён), `REJECTED` (отклонён), `SUPERSEDED` (заменён исправлением) |
| `supersedesId` | у исправленного факта: какой факт он заменил |
| `updatedBy` | кто последний менял: `USER` или `SYSTEM` |

Исправление не переписывает факт. Появляется новая строка, а старая получает статус `SUPERSEDED`. Так видно, что было и что стало.

### Deadline — срок

Строка появляется для факта-срока. Связана с фактом (`claimId`): удалили факт — удалился и срок.

| Поле | Что это |
|---|---|
| `date` | дата срока. Хранится как полночь по UTC, время не важно |
| `kind` | ответ, документы, возражение (Widerspruch), напомнить позже |
| `doneAt` | когда пользователь отметил «сделано» |

### Event — история дела

Записи вида «письмо получено», «факт подтверждён», «черновик отправлен». `details`: подробности.

### Message — вопросы по делу

Вопросы пользователя (`role = USER`) и ответы помощника (`ASSISTANT`) внутри дела. Переписка общего чат-помощника в базе не хранится.

### Draft — черновик ответа

| Поле | Что это |
|---|---|
| `kind` | вид ответа: запрос уточнения, документы, продление срока и др. |
| `germanText`, `russianText` | текст письма по-немецки и перевод для пользователя |
| `claimIds`, `claimSnapshot` | из каких фактов собран черновик и какими были их значения в этот момент |
| `stale` | `true`: факт изменился после сборки, черновик надо собрать заново |
| `verification` | результат автоматической проверки черновика |
| `status`, `sentAt`, `sentVia` | подготовлен или отправлен, когда и как |

### LlmCall — журнал обращений к модели

Каждое обращение к языковой модели: какой промпт, какая модель, сколько длилось, удачно ли. Текст в журнале уже замаскирован (без имён, адресов, номеров).

Таблица специально не связана с другими. Поэтому при удалении кабинета, дела или письма эти строки удаляет код по `cabinetId`, `caseId` или `letterId` (задача A01). Вопросы гостя к чат-помощнику пишутся с пустым `cabinetId` и только первыми 200 знаками.

### AccountErasure — задание удаления аккаунта (A01)

Одно задание на кабинет (`cabinetId` уникален). Без связи с Cabinet: задание переживает удаление кабинета. После успешной очистки строка удаляется целиком, ничего о пользователе не остаётся.

| Поле | Что это |
|---|---|
| `status` | `PREPARING` блокировка поставлена · `FILES_MOVED` файлы в корзине `STORAGE_DIR/trash/<id>` · `DB_DELETED` строки удалены, осталась очистка · `RESTORING` удаление не удалось, файлы возвращаются |
| `leaseOwner`, `leaseUntil` | аренда: задание выполняет только один обработчик (запрос или фоновый повтор). Аренда умершего процесса истекает через 2 минуты |
| `attempts` | сколько раз задание брали в работу |
| `lastError` | этап и тип ошибки, например `cleanup: EBUSY`. Без путей и персональных данных |

Порядок: блокировка (`deletingAt`) → папка писем в корзину → одна транзакция (LlmCall кабинета, его писем и дел; кабинет каскадом; статус) → удаление корзины и дополнительные очистки → строка задания удаляется. Сбой до удаления базы: файлы возвращаются, только потом снимается блокировка. Незаконченные задания сервер повторяет при запуске и каждые 5 минут.

## Что проверяет тест

`api/src/prisma/prisma.cascade.spec.ts` создаёт кабинет со всеми таблицами и удаляет его. После удаления у кабинета не остаётся сессий, дел, писем, фактов, сроков, истории и черновиков. Соседний кабинет при этом не меняется.
