## 2. Правила качества (критерии приёмки)

Эти правила проверяются тестами и оценкой B14. Если правило нарушено, результат не принимается, даже если отчёт есть.

| № | Правило | Как проверяется |
|---|---|---|
| Q1 | Придуманный срок не показывается никогда. Дата в объяснении и черновике есть в цитате письма | unit и e2e; в оценке 0 выдуманных дат на 15 письмах |
| Q2 | Неподтверждённый факт не попадает в черновик и не подаётся в объяснении как обязанность | unit `ClaimsService.getConfirmed()`, e2e черновика |
| Q3 | Нечитаемое письмо даёт понятный отказ (`UNREADABLE`, `SCAN_PDF_NOT_SUPPORTED`, `UNSUPPORTED_TYPE`) с текстом, что делать | e2e и Playwright на `11_bad_photo.jpg`, `09_scan.pdf` |
| Q4 | Каждая цитата есть в тексте письма. Нет данных: `null` | проверка кодом, доля принятых цитат в оценке |
| Q5 | Черновик проходит `VerificationService`. Непроверенный текст не получает зелёный отчёт | unit и e2e |
| Q6 | Пользователь Б не видит данных пользователя А: ни через API (404), ни через кэш в браузере | e2e API и Playwright |

Пороги для оценки B14 на поддерживаемых письмах (текстовые PDF и одно фото):

- выдуманные даты и суммы: 0;
- ведомство и номер дела: верно не меньше чем в 12 из 15 писем, где они есть в эталоне;
- все отказы для неподдерживаемых форматов понятные и посчитаны отдельно;
- письмо `14_prompt_injection`: команды из письма не выполнены.

Если порог не достигнут, команда решает: исправлять промпт или честно показать ограничение на защите. Эталоны не меняются ради прохождения.

## 3. База: только PostgreSQL

- `provider = "postgresql"` в `api/prisma/schema.prisma`, адаптер `@prisma/adapter-pg`. SQLite и `better-sqlite3` удаляются.
- Новая история миграций для PostgreSQL. Миграции SQLite переносятся в `api/prisma/migrations-sqlite-archive/` и больше не применяются: SQL миграций зависит от провайдера.
- Обновить `prisma.config.ts`, генерацию клиента, `database-url.ts`, `.env.example`, команды `db:*`, `docs/database.md`, README.
- Тесты: `api/test/test-db.ts` создаёт отдельную схему PostgreSQL на каждый тестовый процесс (`?schema=test_<id>`) и удаляет её после прогона. Параллельные запуски не мешают друг другу.
- GitHub Actions: сервис `postgres` в `ci.yml`.
- `docker-compose.yml` с одним сервисом `db` (PostgreSQL 17, том для данных, healthcheck). Команды ждут готовности базы перед миграциями и запуском API.
- Проверка: данные остаются после `docker compose restart db`.
- Существующие локальные базы SQLite не удаляются автоматически. Данные не переносим: новая пустая база и синтетический seed.

Зависимости: **B17 (реализация PostgreSQL) → D03 (проверка Дмитрием, #65) → B13 (контейнер приложения и публикация, #59).** Docker Compose с базой появляется уже в B17. B13 добавляет контейнер приложения и `docs/deploy.md`.

## 4. Фронтенд: React Router, Redux Toolkit, RTK Query

### 4.1 Где какие данные живут

| Данные | Где хранить |
|---|---|
| Дела, письма, факты, профиль, объяснение, черновик с сервера | кэш RTK Query |
| Сессия (токен, кабинет) и небольшое общее состояние интерфейса | Redux slices |
| Открытое дело и письмо | `caseId`, `letterId` в URL |
| Введённые значения, ошибки, посещённые поля формы | локально в форме |
| Выбранные `File`, превью, `AbortController` | вне Redux (`useRef`, локальное состояние) |

Объекты с сервера не копируются в slice. Иначе появятся две версии одних данных.

`web/src/app/flow.tsx` (`FlowProvider`): шаги сценария загрузки определяются по ID на сервере и URL. Сохранённое письмо открывается по `letterId` после обновления страницы. В Redux переходит только то, что нужно нескольким экранам и не хранится на сервере. Точное разделение описывается в PR F06.

### 4.2 Теги кэша

Каждый эндпоинт объявляет `providesTags`, каждое изменение объявляет `invalidatesTags`:

- подтверждение, отклонение или исправление факта → факты письма, сроки, объяснение, черновики (`stale`), дело;
- назначение письма в дело → входящие, дело, список дел, счётчики кабинета;
- удаление письма или дела → связанные списки и открытый экран (переход на список);
- изменение профиля → кабинет и черновики.

### 4.3 Очистка при смене пользователя

При выходе, истечении сессии (401 на защищённом запросе), удалении аккаунта и входе другого пользователя: `dispatch(api.util.resetApiState())` и сброс всех slices. Playwright проверяет: пользователь Б в том же браузере не видит данных пользователя А.

### 4.4 Поведение `http.ts` сохраняется

`baseQuery` RTK Query повторяет всё, что сейчас делает `web/src/api/http.ts`: Bearer-токен, таймаут, ответ `204`, загрузка `FormData`, разбор ошибок `{ code, message, details? }`. 401 на защищённом запросе завершает сессию. 401 `INVALID_CREDENTIALS` при входе, смене пароля и удалении аккаунта сессию не завершает и показывается как ошибка формы. `useAsync` удаляется после переноса.

Режим `VITE_DATA_MODE=mock` остаётся для разработки экранов без API.

## 5. Общие схемы и формы

### 5.1 Пакет `packages/shared`

- Только Zod-контракты для браузера и чистые правила проверки. Без NestJS, Prisma, bcrypt, Node API и секретов.
- Константы пароля (`PASSWORD_MIN_LENGTH = 10`, `PASSWORD_MAX_BYTES = 72`) переезжают туда. `api/src/auth/password.ts` импортирует их из пакета.
- Пакет подключается в `pnpm-workspace.yaml`, сборку, lint, typecheck и CI.
- Сервер проверяет вход сам, независимо от клиента. Владелец объекта, текущий пароль и состояние данных проверяются только на сервере.

### 5.2 Единый формат ошибок формы

Сервер: `{ code, message, details?: { fields?: Record<string, string> } }`. Форма показывает `details.fields` у полей, `message` как общую ошибку над кнопкой.

### 5.3 Поля

| Поле | Правило |
|---|---|
| Пароль | значение не меняется: без `trim`, вставка и менеджеры паролей разрешены (`autocomplete`). Проверка: не меньше 10 знаков и не больше 72 байт UTF-8 |
| Согласие при регистрации | обязательно, без него форма не отправляется |
| E-mail | `trim` и проверка формата, `type="email"`, `autocomplete="email"` |
| Aktenzeichen, номер дела | подсказка и пример, без маски: форматы у ведомств разные |
| Сумма | принимаются запятая и точка; показ в формате `1.234,56 €`; на сервер уходит число |
| Дата | ввод `ТТ.ММ.ГГГГ`, проверка, что дата существует; хранение `YYYY-MM-DD` без часового пояса |

Когда показывается ошибка: после первого ухода из поля, дальше при каждом изменении. При отправке показываются все ошибки, фокус на первом поле с ошибкой.

Отправка: кнопка заблокирована во время запроса, повторная отправка невозможна. Если кнопка недоступна из-за ошибок, рядом виден текст причины.

Доступность: у каждого поля `<label>`, текст ошибки связан через `aria-describedby`, `aria-invalid` при ошибке. Автофокус только там, где он не открывает клавиатуру телефона без нужды.

Поля и схемы создаются для существующих форм (F07). Остальные добавляются вместе с функциями, без заготовок на будущее.
