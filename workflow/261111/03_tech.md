# ТЗ для Codex: бэкенд «Разберёмся»

Модульный монолит на NestJS для ведения переписки с немецкими ведомствами. Версия 1.0, срок сдачи проекта 03.12.2026.

## 1. Цель и контекст

**Продукт.** Помощник для русскоязычных людей, недавно приехавших в Германию и самостоятельно ведущих переписку с ведомствами.

**Проблема.** Ведомство повторно запрашивает документы, а человек уверен, что уже отправил их.

**Что делает система.**

1. Принимает письмо ведомства (PDF, фото или скан), извлекает ведомство, номер дела, требования и срок. К каждому полю прилагаются цитата из письма и уверенность.
2. Привязывает письмо к делу по номеру дела и ведёт хронологию.
3. Фиксирует слова пользователя («я уже отправил») как утверждения с источником USER, а не как факты.
4. Пересматривает выводы, когда приходит новый документ, и объясняет изменение.
5. Готовит черновик ответа (немецкий текст и пояснение на русском) **только из подтверждённых утверждений**, после проверки кодом.

ИИ извлекает данные и формулирует текст. Порядок шагов, статусы, сроки и проверки выполняет обычный код. Решение о подтверждении связи писем и утверждений принимает человек.

**Ограничения.** Команда из пяти начинающих разработчиков, три недели, параллельная работа. Поэтому архитектура максимально простая и чётко разделена по модулям.

## 2. Объём

**Входит в MVP:** загрузка PDF, фото и сканов (JPG, PNG), распознавание текста (OCR), извлечение, с

оздание дел и связывание, хронология и ближайший срок, диалог с уточнениями, пересмотр утверждений, черновик с проверкой, трассировка вызовов LLM, прогон eval на синтетических письмах, Swagger.

**Если останется время:** тонкий React-интерфейс поверх REST.

**Вне рамок:** отправка писем в ведомства, аутентификация и многопользовательность, отдельные микросервисы, юридические консультации.

## 3. Обязательные правила (нарушение = задача не принята)

1. **Связность модулей.** Модули не вызывают друг друга напрямую. Данные идут только через `CasesModule`, порядок шагов задаёт только `WorkflowModule`. Единственное разрешённое исключение: инфраструктурные `ConfigModule` и `LlmModule` могут импортироваться любым модулем.
2. **Единый вход в LLM.** Любой вызов модели делается только через `LlmService`. Ответ проверяется по схеме Zod, при ошибке выполняется ограниченный повтор, каждый вызов (успешный и неуспешный) пишется в `LlmCall`, и только после этого результат попадает в состояние дела. Прямые импорты SDK провайдера вне `llm/` запрещены (проверить правилом ESLint `no-restricted-imports`).
3. **Только подтверждённые факты в черновике.** `DraftService.generate()` принимает по типу только `ConfirmedClaim[]`. Тип нельзя получить иначе как через `CasesService.getConfirmedClaims()`. Компилятор, а не только промпт, не даёт передать неподтверждённое утверждение.
4. **Промпты как файлы.** Промпты лежат в `src/llm/prompts/<имя>.v<N>.md`, версия записывается в каждый `LlmCall`. Старые версии не изменяются, только добавляются новые.
5. **Утверждение пользователя не равно факту.** Всё, что пользователь сообщил, сохраняется с `basis = USER`, `status = UNCONFIRMED`, пока не появится подтверждение (документ или явное действие пользователя по согласованному правилу).
6. **Ничего не выдумывать.** Если поле не найдено в письме, возвращается `null` с низкой уверенностью, а не догадка. Цитата в извлечённом поле обязана быть подстрокой исходного текста (проверка кодом; для текста после OCR сравнение идёт после нормализации пробелов и переносов строк и допускает небольшое расстояние редактирования, порог настраивается).

## 4. Стек

NestJS (TypeScript, strict), Prisma + PostgreSQL (для локального старта допускается SQLite, схема должна работать на обеих), Zod, библиотека извлечения текста из PDF (например `pdf-parse`), tesseract.js для OCR (язык deu), sharp для предобработки изображений, растеризация страниц PDF (pdfjs-dist или pdftoppm), Jest, `@nestjs/swagger`, ESLint и Prettier. Менеджер пакетов: pnpm. Ключи и параметры только из переменных окружения через `ConfigService`, файл `.env.example` обязателен.

## 6. Модули

### ConfigModule (глобальный)

Переменные окружения и API-ключи. `ConfigService` валидирует окружение схемой Zod при старте и падает с понятной ошибкой, если чего-то нет.

### LlmModule

- `LlmService.call<T>({ promptName, promptVersion?, variables, schema: ZodType<T> }): Promise<T>`: подставляет переменные, вызывает модель, парсит JSON, валидирует по схеме, при ошибке повторяет до 2 раз (в повторный запрос добавляется текст ошибки валидации), иначе бросает `LlmValidationError`.
- `PromptRegistry`: загружает файлы из `llm/prompts/`, отдаёт последнюю версию по умолчанию, поддерживает явный выбор версии.
- `TraceService`: пишет `LlmCall` (версия промпта, вход, выход, длительность, токены, признак ошибки) и отдаёт список для `GET /cases/:id/trace`. Вызов привязывается к делу через контекст (`caseId` передаётся в `call`).
- Провайдер модели скрыт за интерфейсом `LlmProvider`. В тестах используется `FakeLlmProvider` с заданными ответами.

### DocumentsModule

`DocumentsService.parse(file): { text, pages[], source, readable, ocrConfidence?, reason? }`, где `source` равен `TEXT_LAYER` или `OCR`. Принимает PDF, JPG и PNG (до 10 МБ, для PDF до 20 страниц). Для PDF сначала берётся текстовый слой; если текста меньше порога (по умолчанию 200 символов на документ), страницы растеризуются и передаются в `OcrService`. Фото и изображения сразу идут в `OcrService`.

`OcrService.recognize(images): { pages: { text, confidence }[] }` использует Tesseract с языком `deu` и предобработкой: градации серого, выравнивание и поворот, бинаризация, масштабирование примерно до 300 DPI. Распознаётся печатный текст; рукописный текст не поддерживается.

Проверка читаемости: если распознанного текста меньше порога или средняя уверенность OCR ниже порога (по умолчанию 60 из 100), возвращается `readable = false` с причиной «плохое качество изображения, загрузите более чёткий снимок или скан». Уверенность OCR по странице передаётся дальше: `confidence` поля, найденного на этой странице, не может быть выше неё. Оба порога задаются через `ConfigService`.

### ExtractionModule

`ExtractionService.extract(text): ExtractedLetter` через `LlmService`. Схема `ExtractedLetter`:

```ts
const Field = <T extends z.ZodTypeAny>(v: T) => z.object({
  value: v.nullable(),
  quote: z.string().nullable(),      // подстрока исходного текста
  page: z.number().int().nullable(),
  confidence: z.number().min(0).max(1),
});
export const ExtractedLetter = z.object({
  authority: Field(z.string()),
  caseNumber: Field(z.string()),
  letterDate: Field(z.string()),     // ISO 8601
  requirements: z.array(Field(z.string())),
  deadlines: z.array(z.object({
    date: z.string(),                // ISO 8601
    kind: z.enum(['REPLY', 'DOCUMENTS']),
    quote: z.string(), page: z.number().int().nullable(),
    confidence: z.number().min(0).max(1),
  })),
});
```

После ответа модели код проверяет, что каждая `quote` встречается в исходном тексте (для OCR-текста сравнение нормализованное, как в правиле 6); невалидные цитаты обнуляют значение и снижают уверенность до 0.

### CasesModule

Единственный владелец данных дела. Все остальные модули читают и пишут только через его сервисы.

- `CasesService`: создание дела, получение состояния, `addClaims`, `supersedeClaims`, `getConfirmedClaims(caseId): ConfirmedClaim[]`, сохранение `Draft`.
- `LinkingService`: по номеру дела предлагает связь письма с существующим делом (создаёт запись предложения связи, статус PENDING), `confirm(linkId)` применяет связь. Автоматически ничего не привязывается без подтверждения человека.
- `TimelineService`: собирает хронологию из `Event`, считает ближайший срок из `Deadline` (только не просроченные, по возрастанию даты) и список открытых вопросов (утверждения UNCONFIRMED и недостающие поля).

### DialogueModule

- `DialogueService.handle(caseId, message)`: через `LlmService` разбирает сообщение пользователя на утверждения (`basis = USER`) и формирует не более 3 уточняющих вопросов, если данных не хватает. Пример: «я уже отправил документы» → утверждение «пользователь утверждает, что отправил документы» с запросом даты и способа отправки.
- `RevisionService.revise(caseId, newClaims)`: при новом документе определяет затронутые утверждения, меняет их статус на `SUPERSEDED`, записывает `supersededById` и человекочитаемую `reason` на русском (объяснение пользователю), создаёт `Event` типа «пересмотр».

### DraftingModule

- `DraftService.generate(claims: ConfirmedClaim[], context): { germanText, russianExplanation, usedClaimIds }` через `LlmService`.
- `VerificationService.verify(draft, claims)`: проверка кодом, без LLM. Минимум: все числа, даты и номера дел из черновика присутствуют среди подтверждённых утверждений; номер дела в черновике совпадает с делом; нет дат из прошлого как будущих сроков; `usedClaimIds` является подмножеством переданных. Возвращает отчёт `{ passed, checks[], checklist[] }`, где `checklist` показывает каждый факт и его источник.
- При непройденной проверке черновик сохраняется со статусом `PREPARED` только если `passed = true`; иначе возвращается отчёт об ошибках и `Draft` не создаётся.

### WorkflowModule

`CaseWorkflowService` знает все модули и вызывает их в фиксированном порядке; в нём REST-контроллеры. Единственное место с бизнес-последовательностью.

- `ingestLetter(caseId, file)`: parse → если `readable = false`, вернуть ошибку 422 с причиной → extract → сохранить `Letter`, `Claim` (basis DOCUMENT), `Deadline`, `Event` → `LinkingService` предлагает связь → при подтверждённой связи вызвать `RevisionService`.
- `handleMessage(caseId, text)`: сохранить `Message` → `DialogueService.handle` → сохранить утверждения и `Event` → вернуть вопросы и обновлённое состояние.
- `prepareDraft(caseId)`: взять `getConfirmedClaims` → `generate` → `verify` → сохранить или вернуть отчёт.

### EvalModule

CLI `pnpm eval`. Читает `fixtures/letters/*.json` (письмо + ожидаемые значения), прогоняет извлечение, считает метрики и печатает таблицу, сохраняет JSON-отчёт с версиями промптов.

## 7. Модель данных (Prisma)

Сущности: `Case(id, title, status)`, `Letter(caseId, rawText, sourceType, ocrConfidence, authority, caseNumber, letterDate)`, `Claim`, `Deadline(caseId, date, claimId, kind)`, `Event(caseId, type, at)`, `Message(caseId, role, text)`, `Draft(caseId, germanText, russianExplanation, claimIds, status)`, `LlmCall`.

```prisma
enum ClaimBasis  { DOCUMENT USER ASSUMPTION }
enum ClaimStatus { CONFIRMED UNCONFIRMED SUPERSEDED }

model Claim {
  id           String      @id @default(cuid())
  caseId       String
  text         String
  basis        ClaimBasis
  status       ClaimStatus
  quote        String?
  page         Int?
  confidence   Float?
  supersededById String?
  reason       String?
  createdAt    DateTime    @default(now())
}
```

Остальные модели пишутся аналогично по таблице полей выше, с внешними ключами на `Case`. Допущения, которые нужно зафиксировать в схеме: `Case.status` ∈ {OPEN, CLOSED}; `Event.type` ∈ {LETTER\_RECEIVED, USER\_REPORTED\_SENT, REVISION}; `Draft.status` пока только `PREPARED`; Letter.sourceType ∈ {PDF\_TEXT, PDF\_SCAN, IMAGE}, Letter.ocrConfidence — число от 0 до 100 или null; дополнительно введена сущность `LinkSuggestion(id, caseId, letterId, targetCaseId, status: PENDING|CONFIRMED|REJECTED)`, так как API ссылается на `linkId`, а в исходной модели её нет.

Переходы статуса утверждения: `UNCONFIRMED → CONFIRMED`, `UNCONFIRMED|CONFIRMED → SUPERSEDED`. Обратных переходов нет, историю не удаляем.

Ключевой тип для правила 3:

```ts
declare const brand: unique symbol;
export type ConfirmedClaim = Claim & { status: 'CONFIRMED'; readonly [brand]: true };
// создаётся только внутри CasesService.getConfirmedClaims()
```

## 8. REST API

| Метод и путь | Назначение | Ответ |
| --- | --- | --- |
| `POST /cases` | создать дело | `Case` |
| `POST /cases/:id/letters` (multipart, поле `file`) | загрузка PDF, JPG или PNG → OCR при необходимости, извлечение + предложение связи | извлечённые поля, `linkSuggestion?` |
| `GET /cases/:id` | состояние | хронология, утверждения, ближайший срок, открытые вопросы |
| `POST /cases/:id/links/:linkId/confirm` | подтвердить связь | обновлённое состояние |
| `POST /cases/:id/messages` (`{ text }`) | сообщение пользователя | уточняющие вопросы + состояние |
| `POST /cases/:id/draft` | черновик + отчёт о проверке | `Draft` и отчёт, либо 422 с отчётом |
| `GET /cases/:id/trace` | вызовы LLM | список `LlmCall` |

Все DTO валидируются Zod (или class-validator, но единообразно), единый формат ошибок `{ code, message, details? }`, Swagger-документация на всех endpoint.

## 9. Обработка ошибок

| Ситуация | Поведение |
| --- | --- |
| Файл нечитаем даже после OCR, неподдерживаемый формат или превышен размер | 422, причина, дело не изменяется |
| LLM недоступен или ответ не прошёл схему после повторов | 502 с `code`, сохранён `LlmCall` с ошибкой, состояние дела не изменено |
| Номер дела не найден в письме | письмо сохраняется без связи, в открытых вопросах появляется запрос номера |
| Нет подтверждённых утверждений | `POST /draft` возвращает 409 с пояснением, что нужно подтвердить |
| Проверка черновика не пройдена | 422 с отчётом, черновик не сохраняется |

## 10. Тесты и метрики качества

- Юнит-тесты (Jest) на каждый сервис; LLM везде заменён `FakeLlmProvider`.
- Тест компиляции для правила 3: файл с намеренно неверным вызовом `generate(unconfirmedClaims)` должен не проходить `tsc` (через `// @ts-expect-error`).
- Интеграционные тесты сценариев `ingestLetter`, `handleMessage`, `prepareDraft` на тестовой БД.
- `fixtures/letters/`: не менее 12 синтетических писем (разные ведомства, с номером дела и без, с несколькими сроками, PDF с текстовым слоем и без него, фото письма, скан среднего и плохого качества, повторный запрос документов) с ожидаемыми значениями.
- Метрики eval: точность извлечения по полям отдельно для текстовых PDF и для OCR-источников (фото, сканы) (ведомство, номер дела, срок), доля цитат, найденных в тексте (цель 100%), доля черновиков, прошедших проверку, средняя задержка и токены на вызов.

## 13. Открытые вопросы для команды

1. Какой провайдер и модель LLM используем, каков бюджет на eval.
2. Правило перехода утверждения USER из UNCONFIRMED в CONFIRMED: только по документу, или также по явному подтверждению пользователя с указанием даты отправки.
3. Нужна ли сущность `LinkSuggestion` в таком виде (в исходной модели данных её нет, а в API есть `linkId`).
4. OCR: движок (локальный Tesseract по умолчанию или облачный сервис, с учётом персональных данных в письмах), порог читаемости, порог уверенности OCR и целевые значения метрик eval.
5. Язык и формат сообщений об ошибках для пользователя (русский для пользовательских, английский для технических).
