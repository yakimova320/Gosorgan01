## 1. Что уже есть в бэкенде

Эндпоинты (`src/workflow/cases.controller.ts`):

1. `POST /cases` создать дело по названию.
2. `GET /cases/:id` состояние одного дела: письма, утверждения, сроки, события, сообщения, черновики, `timeline`, `nearestDeadline`, `openQuestions`.
3. `POST /cases/:id/letters` загрузить один файл (PDF, JPG, PNG, до 10 МБ, до 20 страниц) в существующее дело.
4. `POST /cases/:id/messages` сообщение пользователя; ответ: до трёх уточняющих вопросов.
5. `POST /cases/:id/links/:linkId/confirm` перенести письмо в предложенное дело.
6. `POST /cases/:id/claims/:claimId/confirm` человек подтвердил цитату.
7. `POST /cases/:id/draft` черновик запроса уточнения из подтверждённых утверждений.
8. `GET /cases/:id/trace` трасса вызовов LLM.

Сильные стороны, которые сохраняем без изменений: цитата обязана быть в тексте письма (`extraction.service.ts`), черновик строится только из `ConfirmedClaim` (`cases/types.ts`), проверка черновика кодом (`drafting/verification.service.ts`), каждый вызов LLM пишется в `LlmCall`, промпты лежат файлами с версиями.

## 2. Решения команды от 13.11.2026

Решение 1. Факты по-прежнему подтверждает человек. Интерфейс получает шаг «Проверьте, правильно ли Ja!sno понял письмо». Бэкенд добавляет массовое подтверждение и отметку «неверно».

Решение 2. Письмо загружается без заранее созданного дела, во «входящие». После разбора человек выбирает: в существующее дело, в новое дело или не сохранять.

Решение 3. Ответов несколько видов: отправить документы, запросить уточнение, попросить продлить срок, узнать статус. Плюс собственные письма по шаблонам без входящего письма: расторжение (Kündigung), сообщение об изменениях (Änderungsmitteilung), новый банковский счёт, жалоба (Beschwerde), запрос статуса (Sachstandsanfrage), продление срока (Fristverlängerung), свободное письмо.

Решение 4. Личный кабинет с классической регистрацией: e-mail и пароль. Человек регистрируется один раз, потом входит с e-mail и паролем. После входа браузер получает токен сессии на 30 дней. Вход нужен до загрузки первого письма, потому что каждое письмо принадлежит кабинету. В кабинете лежат все дела, история и данные профиля для писем. Это заменяет правило из брифа проекта «доступ без аккаунтов, по секретному токену». Письма с сайта (подтверждение e-mail, сброс пароля) до защиты не отправляются.

Решение 5. Возражение (Widerspruch) и другие юридические вопросы Ja!sno не пишет. Пользователь получает отсылку к консультации (Migrationsberatung, Verbraucherzentrale, адвокат). Шаблона Widerspruch нет. Это уже заложено в `dialogue/dialogue.service.ts`, теперь так же работает выбор вида ответа.

Решение 6. Тексты интерфейса и объяснений к защите только на русском. Параметр языка `lang` вводится сразу, остальные языки (украинский, простой немецкий и другие) подключаются после защиты.

## 3. Схема данных (Prisma)

Менять оба файла: `prisma/schema.prisma` (SQLite) и `prisma/schema.postgres.prisma`. Новая миграция, старые данные в `dev.db` можно пересоздать.

Новые модели `Cabinet` и `Session`:

```prisma
model Cabinet {
  id           String    @id @default(cuid())
  email        String    @unique   // в нижнем регистре, без пробелов
  passwordHash String              // bcrypt; сам пароль не хранится
  language     String    @default("ru")
  profile      Json?               // { firstName, lastName, address, numbers: [{label, value}] }
  consentAt    DateTime            // согласие с Datenschutz при регистрации
  createdAt    DateTime  @default(now())
  lastSeenAt   DateTime  @default(now())
  cases        Case[]
  letters      Letter[]
  sessions     Session[]
}

model Session {
  id         String   @id @default(cuid())
  cabinetId  String
  cabinet    Cabinet  @relation(fields: [cabinetId], references: [id], onDelete: Cascade)
  tokenHash  String   @unique   // sha256 от токена сессии
  expiresAt  DateTime           // создание + 30 дней
  createdAt  DateTime @default(now())
  lastSeenAt DateTime @default(now())
}
```

E-mail хранится только в `Cabinet.email`. В `profile` поля e-mail нет: для писем ведомствам берётся `Cabinet.email`.

Изменения в существующих моделях:

1. `Case`: поле `cabinetId` (обязательное) и `origin` с enum `CaseOrigin { INCOMING OUTGOING }`. `OUTGOING` значит, что дело началось с собственного письма. Поле `updatedAt DateTime @updatedAt`.
2. `Letter`: `caseId` становится необязательным (`String?`), письмо без дела лежит во входящих. Новые поля: `cabinetId`, `fileKey String?` (путь к оригиналу в хранилище), `fileMime String?`, `pages Json` (массив `{ n, confidence, readable }`), `explanation Json?` (кэш объяснения), `masked Boolean @default(true)`.
3. `ClaimStatus`: добавить `REJECTED` для отметки «неверно».
4. `Deadline`: поля `doneAt DateTime?` и `remindDaysBefore Int @default(3)`.
5. `Message`: поле `kind String` со значениями `QUESTION`, `STATEMENT`, `ANSWER`.
6. `Draft`: enum `DraftKind { CLARIFICATION DOCUMENTS EXTENSION STATUS_REQUEST TEMPLATE FREE }`, поля `kind`, `templateId String?`, `recipient Json?`, `sentAt DateTime?`, `sentVia String?`. В `DraftStatus` добавить `SENT`.
7. `EventType`: добавить `QUESTION_ASKED`, `DRAFT_PREPARED`, `DRAFT_SENT`, `DEADLINE_DONE`, `CASE_CREATED_FROM_LETTER`. Значение `USER_REPORTED_SENT` остаётся только для утверждений вида «я уже отправил».

Статус дела для интерфейса («Нужны документы», «Ждём решения», «Завершено» и шаг 1–4) в базе не хранится. Его считает код в `cases/timeline.service.ts` по срокам, черновикам и событиям, функция `stage(case)` с юнит-тестом:

1. `CLOSED` → «Завершено».
2. есть подтверждённый срок без `doneAt` → «Нужны документы» или «Нужен ответ» (по `Deadline.kind`).
3. последний черновик в статусе `SENT` и открытых сроков нет → «Ждём ответа ведомства».
4. иначе → «Нужна проверка» (есть неподтверждённые утверждения) или «Открыто».

## 4. API

Все эндпоинты, кроме `POST /auth/register` и `POST /auth/login`, требуют заголовок `Authorization: Bearer <токен сессии>`. Guard находит `Session` по `sha256(токен)`, проверяет `expiresAt` и обновляет `lastSeenAt` у сессии и кабинета. Нет сессии или срок вышел: 401. Любой запрос к чужому делу, письму или черновику отвечает 404, а не 403, чтобы не раскрывать, что объект существует. Существующие эндпоинты раздела 1 остаются и получают ту же проверку.

Регистрация и вход:

1. `POST /auth/register` → `{ email, password, consent: true }`. Проверка Zod: e-mail корректный, пароль от 10 до 128 знаков, `consent` обязательно `true`. Пароль хэшируется библиотекой `bcryptjs` (cost 12, без сборки нативного кода). Создаёт `Cabinet` (`consentAt = now`) и `Session`, отвечает `201 { sessionToken }`. Токен сессии 32 случайных байта в base64url. Ошибки: 409 `EMAIL_TAKEN`, 400 `CONSENT_REQUIRED`, 400 `VALIDATION_FAILED`.
2. `POST /auth/login` → `{ email, password }`. Отвечает `200 { sessionToken }`. Неверный пароль и неизвестный e-mail дают одну и ту же ошибку 401 `INVALID_CREDENTIALS`, чтобы по ответу нельзя было подбирать пароль к конкретному человеку. После 5 неудачных попыток на один e-mail за 15 минут: 429 `RATE_LIMITED` (счётчик в памяти сервера, для демо этого хватает).
3. `POST /auth/logout` → удаляет текущую `Session`, `204`.

Кабинет:

4. `GET /cabinet` → e-mail, профиль, язык, счётчики `{ openTasks, activeCases, archivedLetters }`, ближайший срок по всем делам, ожидающие предложения связи («Новое письмо: относится к делу …?»).
5. `PATCH /cabinet` → `{ language?, profile? }`, проверка Zod. Смена e-mail и пароля до защиты не делается.
6. `DELETE /cabinet` → `{ password }` для подтверждения. Удаляет кабинет, сессии, все дела, письма, файлы и трассы.

Дела и история:

7. `GET /cases?status=active|done|all&q=` → список `{ id, title, authority, caseNumber, origin, stage, nextDeadline, counts: { letters, questions }, updatedAt }`.
8. `GET /cases/:id` (есть) дополнить полями `stage` и `timelineItems`: готовые для экрана пункты `{ type, at, title, subtitle, letterId?, draftId? }`.
9. `PATCH /cases/:id` → `{ title?, status? }`.
10. `DELETE /cases/:id`.
11. `GET /history?type=letter|question|sent&q=&cursor=` → записи всех дел по дате, по 30 штук.

Входящие письма (сценарий «Загрузить письмо»):

12. `POST /letters` multipart: `files[]` (1 PDF или до 10 изображений, вместе до 20 МБ), поле `mask` (по умолчанию `true`). Ответ: письмо с `caseId = null`, страницы с качеством, извлечённые поля, утверждения со статусом `UNCONFIRMED`, предложения дела `[{ caseId, title, reason }]`. Если хоть одна страница нечитаема, ответ 422 с `details.pages`, в которых указан номер плохой страницы.
13. `GET /letters/:id` → письмо, утверждения с цитатами, объяснение.
14. `GET /letters/:id/file?page=n` → оригинал страницы.
15. `POST /letters/:id/claims/confirm` → `{ confirm: [claimId], reject: [claimId] }`, одна транзакция, события `CLAIM_CONFIRMED`.
16. `POST /letters/:id/assign` → `{ caseId }` или `{ newCase: { title? } }`. Переносит письмо, утверждения и сроки. Если названия нет, код собирает его из ведомства и первого требования, например «Familienkasse: справка из школы». Событие `CASE_CREATED_FROM_LETTER` или `LETTER_RECEIVED`.
17. `DELETE /letters/:id` → «Не сохранять»: письмо, файл, утверждения и трассы этого письма удаляются.
18. `POST /letters/:id/explain?lang=ru` → объяснение (раздел 5), результат кэшируется в `Letter.explanation`.

Существующий `POST /cases/:id/letters` остаётся для кнопки «Добавить письмо в дело» и принимает те же `files[]`.

Диалог:

19. `POST /cases/:id/messages` (есть). Ответ меняется на `{ kind, answer, questions[], state }`. Вопрос пользователя сохраняется как `Message.kind = QUESTION` и событие `QUESTION_ASKED`, утверждение не создаётся. Утверждение (`basis = USER`) создаётся только для `kind = STATEMENT`.
20. `POST /cases/:id/sent` → `{ draftId?, via: post|online|email|other, date }`. Черновик получает `SENT`, событие `DRAFT_SENT`, срок отмечается `doneAt` по флагу `closeDeadlineId`.

Ответы и свои письма:

21. `POST /cases/:id/draft` (есть) принимает `{ kind }`, по умолчанию `CLARIFICATION`. Значение `WIDERSPRUCH` или любой юридический вид отвечает 422 с кодом `LEGAL_REFERRAL`, русским текстом и списком мест для консультации.
22. `GET /templates` → `[{ id, titleRu, titleDe, category, fields: [{ key, labelRu, type, required }] }]`.
23. `POST /outgoing` → `{ templateId, recipient: { name, address }, fields, freeText? }`. Создаёт дело с `origin = OUTGOING` и черновик `TEMPLATE` или `FREE`.
24. `GET /drafts/:id/pdf` → PDF письма (немецкий текст, данные отправителя из профиля, дата, место для подписи).

Сроки:

25. `PATCH /deadlines/:id` → `{ done: true }`, событие `DEADLINE_DONE`.
26. `GET /deadlines/:id/ics` → файл календаря для кнопки «В календарь».

Тексты ошибок: кроме русского `message` в каждом ответе об ошибке есть `code` (уже есть в `workflow/error.filter.ts`). Интерфейс показывает текст по `code`, чтобы позже перевести сообщения.

## 5. LLM: новые и изменённые промпты

Все промпты новыми файлами в `src/llm/prompts/`, старые версии не трогать.

`explain.v1` объясняет письмо простым языком. Вход: утверждения письма с цитатами и язык. Выход по схеме Zod:

```ts
{ about: string,                       // «О чём письмо?», до 400 знаков
  actions: [{ text: string, claimIds: string[] }],  // «Что нужно сделать?», до 5 пунктов
  deadline: { date: string, claimId: string } | null,
  unconfirmed: boolean }               // true, если опирается на неподтверждённые утверждения
```

Проверка кодом, как в `verification.service.ts`: каждая дата и каждое число в тексте есть в цитатах указанных `claimIds`. Не прошло проверку, значит повтор, после трёх попыток 502.

`dialogue.v2` сначала определяет вид сообщения: `QUESTION` или `STATEMENT`. Для вопроса возвращает `answer` до 600 знаков, только по утверждениям дела и тексту писем дела. Если ответа в материалах нет, честно пишет, что в письмах этого нет, и предлагает, где узнать. Проверка юридических слов в коде (`dialogue.service.ts`) остаётся перед вызовом модели.

Ответы видов `DOCUMENTS`, `EXTENSION`, `STATUS_REQUEST` строятся шаблонами в `drafting/templates.ts` без LLM, по образцу нынешнего `CLARIFICATION`. Для каждого вида свой шаблон и своя ветка в проверке `evidence-template`.

Шаблоны собственных писем лежат в `src/drafting/outgoing/<id>.ts`, тоже без LLM. Текст собирается из полей формы и профиля.

`free-letter.v1` нужен только для свободного письма: пользователь пишет по-русски, модель переводит в деловой немецкий. Проверка кодом: в немецком тексте нет чисел, дат и имён, которых нет в тексте пользователя и профиле.

## 6. Данные и безопасность

1. Маскирование перед любым вызовом LLM, новый `src/documents/masking.service.ts`: IBAN, BIC, Steuer-ID (11 цифр), номер социального страхования, телефон, e-mail заменяются метками `[IBAN_1]` и т. п. Таблица замен хранится только в памяти запроса. Цитаты в утверждениях сохраняются по исходному тексту. Юнит-тест на фикстуре с вымышленным IBAN.
2. Оригиналы файлов хранятся в папке `STORAGE_DIR` (переменная окружения, в Docker отдельный том), не в базе. Путь `cabinetId/letterId/page-N.ext`.
3. Удаление: письма, дела и кабинета удаляет и файлы. Автоудаление кабинетов без активности дольше `CABINET_TTL_DAYS` (по умолчанию 90) задачей `@nestjs/schedule` раз в сутки.
4. Пароль, `passwordHash` и токены сессии не пишутся в логи и трассы `LlmCall` и не возвращаются ни в одном ответе API. E-mail кабинета не уходит в LLM и в логах показывается замаскированным (`a***@example.org`).
5. Настоящие документы людей загружаются только после «шлюза пилота» из брифа проекта: хостинг в ЕС, условия обработки данных у провайдера LLM, проверенные Impressum и Datenschutz. До этого работаем на синтетических письмах из `../../fixtures/letters`.
6. E-mail это персональные данные. Datenschutz называет цель (вход в кабинет) и срок хранения. Для «шлюза пилота» нужно ещё восстановление пароля по e-mail, а значит почтовый провайдер в ЕС с договором обработки данных (AVV).
7. Просроченные `Session` удаляются той же ежедневной задачей, что и неактивные кабинеты.

## 7. Исправления в текущем коде

1. `cases.service.ts`, `saveDialogue`: событие `USER_REPORTED_SENT` создаётся на каждое сообщение, даже на вопрос. Создавать только для утверждений об отправке.
2. `dialogue.service.ts` и `saveDialogue`: вопрос пользователя сохраняется как утверждение и потом появляется в `openQuestions` как «Подтвердите утверждение…». Вопрос не должен становиться утверждением.
3. `timeline.service.ts`, `openQuestions`: формулировки рассчитаны на разработчика. Нужны тексты для человека и поле `kind` (`CONFIRM_CLAIM`, `MISSING_CASE_NUMBER`, `MISSING_DEADLINE` и т. д.), по которому интерфейс решает, куда вести пользователя.
4. Предложение связи создаётся только при совпадении `caseNumber` с письмом из другого дела. Добавить совпадение с номерами из профиля кабинета (`profile.numbers`), например Kindergeld-Nr.
5. `Deadline.kind` знает только `REPLY` и `DOCUMENTS`. Добавить `OBJECTION` (срок возражения, только для показа и отсылки к консультации) и `FOLLOW_UP` (собственное напоминание «нет ответа»).
6. `main.ts`: CORS не включён, `HOST` по умолчанию `127.0.0.1`. Нужны `CORS_ORIGIN` в `config.module.ts` и `HOST=0.0.0.0` в Docker. Это то же, что Issue B09.
7. Загрузка принимает ровно один файл (`FileInterceptor('file', { files: 1 })`). Перейти на `FilesInterceptor('files')`, страницы склеивать в одно письмо в `documents.service.ts`.
8. При плохом качестве `documents.service.ts` отвечает одной ошибкой на всё письмо. Качество каждой страницы уже считается (`pages[].confidence`), его нужно вернуть в ответе.

| Ф9 | U11, U13 | виды ответа, PDF, ICS, «я отправил» | Widerspruch → 422 `LEGAL_REFERRAL`; PDF открывается |
| Ф10 | U12 | собственные письма | 6 шаблонов, проверка полей, дело `OUTGOING` создаётся |

Фазы Ф1–Ф7 нужны для демо на защите. Ф8–Ф10 делаются, если останется время.

## 9. Что не делаем до защиты

1. Доступ для помощника или консультанта к делу.
2. Передача фото с телефона на компьютер по QR-коду.
3. Напоминания push и e-mail (в интерфейсе остаётся ICS-файл «В календарь»).
4. Языки кроме русского.
5. Подтверждение e-mail, восстановление пароля по e-mail, вход через Google или Apple, смена e-mail и пароля.

В макетах эти места помечены «скоро».
